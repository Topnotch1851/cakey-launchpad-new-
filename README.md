# Cakey AI — Waitlist site

Next.js 16 (App Router) marketing + waitlist site for Cakey AI. Pure-black
cinematic theme, Spline 3D hero, Supabase-backed waitlist with server actions,
SEO + JSON-LD baked in, deployed to Vercel.

---

## Quick start

```bash
# 1. Install
npm install

# 2. Configure environment (see "Environment" below)
cp .env.example .env.local
# edit .env.local

# 3. Apply the Supabase migration (one-time, see "Database" below)

# 4. Dev server
npm run dev
```

Visit http://localhost:3000.

## Environment

| Var | Scope | Required | Purpose |
|---|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | public | recommended | Absolute URL used in sitemap, OG, JSON-LD canonical links |
| `NEXT_PUBLIC_SUPABASE_URL` | public | yes | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public | yes | Supabase anonymous JWT (RLS-protected) |
| `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` | public | optional | WalletConnect project for RainbowKit |
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` | server | optional | Override the public values for server-only paths; falls back to the `NEXT_PUBLIC_*` ones |
| `SUPABASE_SERVICE_ROLE_KEY` | server | optional | Service-role key for future back-office reads. Never exposed to the browser. |
| `WAITLIST_IP_SALT` | server | **yes in production** | 16+ byte random string used to hash submitter IPs. **Fail-fast on prod**: a missing salt throws and the action returns a misconfiguration error. Dev falls back to a constant. |

Generate a salt:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

`.env.local` is gitignored; `.env.example` documents the template.

## Architecture (waitlist flow)

```
Browser  ──>  React Query mutation  ──>  Server action (joinWaitlistAction)
                                              │
                                              ├─ Zod validation
                                              ├─ Hash submitter IP (SHA-256 + WAITLIST_IP_SALT)
                                              ├─ Read User-Agent
                                              └─ createServerSupabase() ──>  Supabase RPC `join_waitlist`
                                                                                   │
                                                                                   ├─ enforce 5/h per-IP rate limit
                                                                                   ├─ insert into waitlist_signups
                                                                                   └─ return (id, queue_position)
```

The browser never talks to Supabase directly. The anon key is RLS-locked; the
`SECURITY DEFINER` RPC is the only entry point that can write.

### Key directories

```
src/
├── app/                          ← App Router routes (server components default)
├── components/
│   ├── landing/                  ← Marketing UI
│   ├── ui/                       ← shadcn primitives + Spline wrapper
│   └── wallet/                   ← Lazy wallet island (Wagmi + RainbowKit)
├── features/
│   └── waitlist/
│       ├── actions.ts            ← "use server" entry — Zod + IP hash + delegate
│       ├── schemas.ts            ← Zod schemas for email / role / wallet
│       ├── services/
│       │   └── waitlist.service.ts ← Pure service, takes a Supabase client
│       └── hooks/useJoinWaitlist.ts ← React Query mutation around the action
├── lib/
│   ├── env.ts                    ← Public + lazy-server env (Zod)
│   ├── seo/structured-data.ts    ← JSON-LD builders (Org, WebSite, FAQPage, ...)
│   └── supabase/server.ts        ← Anon + service-role clients
└── providers/AppProviders.tsx    ← QueryClient + Toaster + ErrorBoundary (no wallet at root)
```

> **Schema lives elsewhere.** All Supabase migrations — including the
> `waitlist_signups` table and `join_waitlist` RPC this app depends on — are
> owned by `cakey-platform/supabase/migrations/`. The waitlist app is a pure
> client: it calls the RPC via the Supabase JS client and does not own any
> SQL. When the waitlist is decommissioned, deleting this folder leaves the
> schema (and the platform's auth foundation) untouched.

## Database

The migration creates `public.waitlist_signups` + the `join_waitlist(...)` RPC
+ row-level security. RLS denies all direct access to anon; the RPC is the only
entry point.

### Apply to a fresh Supabase project

The migrations have moved. Apply them from
[`cakey-platform/supabase/migrations/`](../cakey-platform/supabase/migrations/)
in numerical order (`0001` through the latest). The waitlist app only needs
`0001` + `0002` to function, but applying the full set keeps the database
ready for the platform and admin apps as well.

### Verify

```sql
-- From the SQL Editor, with an anon JWT:
select * from public.join_waitlist(
  p_email := 'verify@example.com',
  p_role  := 'investor',
  p_ip_hash := 'manual-verify'
);
-- Expect: one row with id + queue_position.

-- Clean up the smoke-test row:
delete from public.waitlist_signups where source = 'mcp_smoke_test';
```

### Rate limit

5 attempts per IP-hash per rolling hour. Raised as PostgreSQL `P0001`
exception, caught in the service layer, returned as
`"Too many signup attempts. Please try again later."`

## Performance choices

- **Spline 3D hero** is idle-deferred (`requestIdleCallback`) so it never blocks
  LCP. The `.splinecode` binary is prefetched via `<link rel="prefetch">` on
  the homepage so it's already cached by the time the runtime imports.
- **Wallet UI** (Wagmi + RainbowKit) is `next/dynamic({ ssr: false })`.
  Marketing pages that don't render `<Waitlist>` ship zero wallet bytes.
- **Feature pages** are statically prerendered at build time via
  `generateStaticParams`.
- **`/scene.splinecode`** is served from `public/` with
  `Cache-Control: public, max-age=31536000, immutable` (see
  [`next.config.ts`](next.config.ts)). When you replace the asset, **rename it**
  (e.g. `scene-v2.splinecode`) and update the import path — otherwise cached
  copies will serve the old one for up to a year.

### Rollback

If a `main` deploy breaks production, roll back to the last good deploy:

**Fastest (Vercel UI, ~30 seconds):**

1. Open https://vercel.com/top-notchs-projects-37088867/cakey-next/deployments
2. Find the last `Ready` deployment with the green check mark.
3. Click the `⋯` menu → **Promote to Production**.

The previous good build is live within seconds. Vercel does not re-trigger a
build because the deployment already exists.

**Code rollback (only if the bad commit needs to leave history):**

```bash
git revert <bad-commit-sha>
git push origin main
# → CI runs → new deploy with the revert
```

Never `git reset --hard` on `main` — it rewrites the shared history and
breaks anyone with a local clone.

### Verifying a deploy

After every prod push:

1. Wait for the green check on the [deployments page](https://vercel.com/top-notchs-projects-37088867/cakey-next/deployments).
2. Hard-refresh https://cakey-next.vercel.app (Ctrl/Cmd-Shift-R) to bypass the old chunks.
3. Submit a test email through the waitlist form. Confirm the row appears in
   the Supabase `waitlist_signups` table.

## Common tasks

### Add a new feature page

1. Add a slug + content to the `FEATURES` map in
   [`src/app/features/[slug]/page.tsx`](src/app/features/%5Bslug%5D/page.tsx).
2. Add the path to the `STATIC_ROUTES` array in
   [`src/app/sitemap.ts`](src/app/sitemap.ts).
3. `generateStaticParams` already picks it up at build time.

### Add a JSON-LD claim to a page

Use the builders in
[`src/lib/seo/structured-data.ts`](src/lib/seo/structured-data.ts):

```tsx
import { StructuredData } from "@/components/StructuredData";
import { combinedGraph, breadcrumbsSchema, webPageSchema } from "@/lib/seo/structured-data";

const pageSchema = combinedGraph(
  webPageSchema({ name: "...", description: "...", url: "/my-page" }),
  breadcrumbsSchema([{ name: "Home", url: "/" }, { name: "My Page", url: "/my-page" }]),
);

export default function MyPage() {
  return (
    <main>
      <StructuredData data={pageSchema} />
      {/* ... */}
    </main>
  );
}
```

### Update the OG image

Edit [`src/app/opengraph-image.tsx`](src/app/opengraph-image.tsx). It runs on
the edge — no external font fetch, system stack only, ~50ms cold start.

## Known limitations / next on the DoD list

The following are deferred until the platform expands beyond the waitlist:

- No automated tests (unit / integration / E2E)
- No Sentry / error tracking
- `useAnalytics` is a console stub (PostHog or similar TBD)
- No Web Vitals reporting
- No CAPTCHA / Turnstile on the form (rate limit alone is bypassed by rotating IPs)
- No email verification / unsubscribe flow
- No staging environment (`main` → prod directly)
- Footer social links are placeholders ("Soon" tags)
- `Insurance → File a claim` is disabled with a "Soon" badge until the protection pool ships

These are tracked in agent memory and will be addressed when the wider platform
build begins.
